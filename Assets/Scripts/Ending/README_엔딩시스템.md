# 엔딩 시스템 사용법

## 구성 파일
- `EndingCondition.cs` : 엔딩 성립 조건 하나 (플래그 참/거짓, 단서 수집 여부, 최소 단서 개수)
- `EndingDefinition.cs` : 엔딩 하나의 데이터 (제목, 본문, 배경 이미지, 조건 목록) — ScriptableObject 에셋
- `EndingManager.cs` : 조건에 맞는 엔딩을 판정하고 엔딩 씬으로 전환하는 싱글턴
- `EndingUIController.cs` : 엔딩 씬에서 제목/본문/배경을 표시하고 재시작·타이틀 버튼을 처리
- `EndingTestTrigger.cs` : 추리 판정 시스템이 없어도 테스트할 수 있는 F10/F11 단축키

저장 시스템(`SaveManager`)의 플래그·단서 수집 목록을 그대로 활용하므로 별도의 데이터 저장소가 필요 없습니다.

## 에디터에서 설정하는 순서

### 1. 엔딩 데이터 에셋 만들기
스크립트가 컴파일된 뒤, Project 창에서 `Assets/Data/Endings` 같은 폴더를 만들고
그 안에서 우클릭 → `Create > 적벽추리 > Ending Definition`으로 엔딩 에셋을 필요한 만큼 만듭니다.

예시로 아래 3개를 만들어보는 것을 추천합니다 (제목/본문은 실제 스토리에 맞게 바꿔주세요):

| 파일명 | endingType | 조건 | 비고 |
|---|---|---|---|
| Ending_True | True | `FlagIsTrue: final_accusation_correct` + `MinClueCount: (전체 단서 개수)` | 진범 지목 성공 + 모든 단서 확보 |
| Ending_Good | Good | `FlagIsTrue: final_accusation_correct` + `MinClueCount: (전체 단서의 절반 정도)` | 진범은 맞혔지만 단서는 일부만 확보 |
| Ending_Bad | Bad | (조건 없음) | 위 두 엔딩에 해당하지 않는 모든 경우 — 반드시 목록 맨 아래 배치 |

### 2. EndingManager 배치
- `SaveManager`가 있는 것과 같은 시작 씬에 빈 GameObject `EndingManager`를 만들고 `EndingManager.cs`를 붙입니다.
- 인스펙터의 `Endings In Priority Order` 리스트에 위에서 만든 엔딩들을
  **엄격한 조건 → 느슨한 조건 → 조건 없음(배드 엔딩)** 순서로 넣습니다.
  (위에서부터 검사해서 맨 처음 조건을 만족하는 것이 선택되기 때문에 순서가 중요합니다.)
- `Ending Scene Name`에는 아래에서 만들 엔딩 전용 씬 이름을 입력합니다 (기본값 `Ending`).

### 3. 엔딩 씬 만들기
- File > New Scene으로 `Ending` 씬을 만들고 File > Build Settings에서 빌드 목록에 추가합니다
  (씬 이름을 EndingManager의 `Ending Scene Name`과 반드시 일치시킵니다).
- Canvas를 하나 만들고 그 아래에 제목용 Text, 본문용 Text, 배경용 Image, 버튼 2개(다시 시작 / 타이틀로)를 배치합니다.
- 같은 Canvas(또는 빈 GameObject)에 `EndingUIController.cs`를 붙이고 인스펙터에 방금 만든
  Text/Image/Button들을 각각 연결합니다.
- `Gameplay Scene Name`, `Title Scene Name`에는 실제 플레이 씬/타이틀 씬 이름을 입력합니다.

### 4. 테스트
- 게임 플레이 씬에 `EndingTestTrigger.cs`를 아무 오브젝트에나 붙입니다.
- Play 모드에서 **F11**을 눌러 "진범을 맞혔다"는 테스트 플래그를 켠 뒤, **F10**을 눌러 엔딩 판정 → 엔딩 씬 전환이 잘 되는지 확인합니다.
- F11 없이 F10만 누르면 조건을 하나도 만족하지 못해 배드 엔딩(조건 없는 엔딩)으로 가는 것도 확인해보세요.
- 실제 추리 판정 시스템이 완성되면, 그 시스템이 결과가 나오는 시점에
  `SaveManager.Instance.SetFlag("final_accusation_correct", true/false)`를 호출하고
  이어서 `EndingManager.Instance.TriggerEnding()`을 호출하도록 연결하면 됩니다.
  `EndingTestTrigger.cs`는 그때 지워도 됩니다.

## 왜 이렇게 만들었는가

**엔딩 데이터를 코드가 아니라 ScriptableObject 에셋으로 분리한 이유** — 추리 게임은 엔딩이
2~3개로 끝나지 않고 계속 늘어나는 경우가 많습니다. 엔딩을 코드에 하드코딩하면 엔딩을
추가하거나 문구를 수정할 때마다 스크립트를 고치고 다시 컴파일해야 하지만, 에셋으로 분리하면
Project 창에서 새 엔딩을 만들고 텍스트만 채우면 되므로 이후 스토리 작업이 훨씬 가벼워집니다.

**조건 판정을 "우선순위가 있는 목록에서 첫 번째로 맞는 것"으로 만든 이유** — 여러 엔딩의
조건이 서로 겹칠 수 있습니다(예: 트루 엔딩 조건은 굿 엔딩 조건을 포함). 이런 경우 "조건에 맞는
엔딩이 여러 개 나오면 뭘 보여줄지"를 명확히 정해야 하는데, 가장 단순하고 예측 가능한 방법이
"엄격한 조건부터 순서대로 검사해서 처음 맞는 것을 채택"하는 방식입니다. 그래서 조건이 없는
엔딩(사실상 항상 성립)은 반드시 맨 마지막에 두어 "이도 저도 아닌 경우"의 안전망 역할을 하게 했습니다.

**엔딩 시스템이 아직 없는 추리 판정 시스템과 "플래그"로만 연결되는 이유** — 지금 단계에서
심문/추리 판정 시스템의 구체적인 모습(어떤 UI로, 어떤 방식으로 범인을 지목하는지)이 아직
정해지지 않았습니다. 엔딩 시스템이 그 시스템의 내부 구조를 직접 알게 만들면 나중에 추리
판정 방식이 바뀔 때마다 엔딩 시스템까지 같이 고쳐야 합니다. 대신 "결과가 나오면 플래그 하나만
설정해달라"는 최소한의 규칙으로만 연결해두면, 추리 판정 시스템을 어떤 방식으로 만들든 엔딩
시스템은 전혀 손댈 필요가 없습니다.

**세이브 슬롯과 별개로 "본 엔딩 기록"을 전역 파일로 따로 저장한 이유** — 저장 슬롯의 진행 상황은
새 게임을 시작하면 사라지지만(정상적인 동작), 플레이어가 지금까지 어떤 엔딩들을 봤는지는
여러 번 플레이해도 계속 쌓여야 의미가 있습니다(엔딩 컬렉션/갤러리 기능의 기반). 그래서 이 기록만
세이브 슬롯 파일과는 별도의 파일(`endings_unlocked.json`)에 저장하도록 분리했습니다.

**엔딩을 별도 씬으로 분리한 이유** — 엔딩은 보통 전체 화면 연출(암전, 타이틀 문구, 크레딧 느낌의
텍스트)이 들어가는데, 이걸 플레이 씬의 UI 위에 얹으면 플레이 중 UI와 뒤섞여 관리가 번거로워집니다.
독립된 씬으로 분리해두면 나중에 엔딩 전용 배경음악이나 연출을 자유롭게 추가하기도 쉽습니다.
